# Skenario Pengujian Whitebox (Basis Path Testing)

Pengujian Whitebox berfokus pada struktur internal atau kode sumber dari perangkat lunak. Pada pengujian ini, metode *Basis Path Testing* digunakan untuk memastikan bahwa setiap jalur independen dalam suatu fungsi atau modul penting telah dieksekusi setidaknya satu kali.

Sebagai sampel pengujian, akan dianalisis fungsi `tarikStore` (Proses Penarikan Tabungan Siswa) yang berada di dalam class `TabunganController.php`.

## 1. Analisis Kode Sumber (Fungsi `tarikStore`)

Fungsi ini bertanggung jawab memproses penarikan saldo tabungan siswa. Kode sumber fungsi dapat dipetakan sebagai berikut:

```php
public function tarikStore(Request $request)
{
    // Node 1: Menerima request, validasi awal, & Query Tabungan
    $validated = $request->validate([
        'siswa_id' => 'required|exists:siswas,id',
        'nominal' => 'required|integer|min:1000',
        'tanggal_mutasi' => 'required|date',
    ]);
    $tabungan = Tabungan::where('siswa_id', $validated['siswa_id'])->first();

    // Node 2 & 3: Evaluasi kondisi ketersediaan data dan kecukupan saldo
    if (!$tabungan || $tabungan->saldo < $validated['nominal']) {
        
        // Node 4: Kondisi tidak terpenuhi (Redirect Error)
        return redirect()->back()->with('error', 'Saldo tabungan tidak mencukupi.');
    }

    // Node 5: Kondisi terpenuhi (Eksekusi transaksi Database)
    DB::transaction(function () use ($validated, $tabungan) {
        $saldoBaru = $tabungan->saldo - $validated['nominal'];
        $tabungan->update(['saldo' => $saldoBaru]);

        MutasiTabungan::create([
            // ... insert data mutasi ...
        ]);
    });

    // Node 6: Pencatatan Log Aktivitas
    AktivitasService::catat('Tarik Tabungan', 'App\Models\Tabungan', $validated['siswa_id'], null, [
        'nominal' => $validated['nominal'],
    ]);

    // Node 7: Transaksi sukses dan redirect
    return redirect()->route('tabungan.tarik')->with('success', 'Penarikan berhasil dicatat.');
}
```

## 2. Flowgraph (Grafik Aliran)

Untuk menghitung jalur logika yang tepat, blok kondisi majemuk (`||`) pada `if (!$tabungan || $tabungan->saldo < $validated['nominal'])` dipisah menjadi dua *predicate node* yang dievaluasi berurutan. Berikut adalah rincian node-nya:

- **Node 1**: Inisialisasi, Validasi Request, dan Query data Tabungan.
- **Node 2**: Evaluasi Kondisi 1 (Apakah variabel `$tabungan` bernilai *NULL* / tidak ditemukan?).
- **Node 3**: Evaluasi Kondisi 2 (Apakah saldo siswa saat ini `<` nominal penarikan?).
- **Node 4**: Aksi Pengecualian (Mengembalikan nilai *Return/Redirect* dengan pesan Error).
- **Node 5**: Aksi Transaksi Utama (Update Saldo & Buat catatan Mutasi di *Database*).
- **Node 6**: Aksi Log (Pencatatan Aktivitas sistem).
- **Node 7**: Aksi Berhasil (Mengembalikan nilai *Return/Redirect* dengan pesan Sukses).
- **Node 8**: Selesai (Titik Akhir / *Exit Point* Konseptual Eksekusi Fungsi).

*Alur Edge (Garis pada Graph):*
1. **1 -> 2**
2. **2 -> 4** (Jalur jika Tabungan = Kosong)
3. **2 -> 3** (Jalur jika Tabungan = Ada)
4. **3 -> 4** (Jalur jika Saldo < Nominal)
5. **3 -> 5** (Jalur jika Saldo >= Nominal)
6. **4 -> 8** (Selesai eksekusi melalui blok error)
7. **5 -> 6**
8. **6 -> 7**
9. **7 -> 8** (Selesai eksekusi melalui blok sukses)

## 3. Perhitungan Cyclomatic Complexity (V(G))

*Cyclomatic Complexity* (Kompleksitas Siklomatis) digunakan untuk menentukan jumlah jalur independen minimum (*Basis Path*) yang perlu diuji agar seluruh baris kode dieksekusi secara merata.

Berdasarkan *Flowgraph* di atas, diketahui:
- **Edge (E):** 9
- **Node (N):** 8
- **Predicate Node (P):** 2 (Node 2 dan Node 3)

Metode Perhitungan:
1. Menggunakan Rumus Node & Edge: **V(G) = E - N + 2**  -->  `9 - 8 + 2 = 3`
2. Menggunakan Rumus Predicate Node: **V(G) = P + 1**  -->  `2 + 1 = 3`

Hasil perhitungan **V(G) adalah 3**, yang berarti terdapat **3 jalur logika independen (Basis Path)** pada fungsi ini yang harus dibuatkan skenario pengujiannya.

## 4. Jalur Independen (Basis Path) & Skenario Pengujian

Berdasarkan *Cyclomatic Complexity*, berikut adalah ekstraksi 3 jalur eksekusi:

* **Path 1 (`1-2-4-8`):** Sistem berhasil memvalidasi *request*, namun data tabungan siswa tidak ditemukan. Eksekusi berhenti di tengah jalan dan langsung me-return pesan *error*.
* **Path 2 (`1-2-3-4-8`):** Sistem berhasil memvalidasi *request*, data tabungan ditemukan, namun saat dievaluasi, jumlah saldo siswa lebih kecil dari nominal yang akan ditarik. Sistem membatalkan penarikan dan me-return pesan *error*.
* **Path 3 (`1-2-3-5-6-7-8`):** Sistem memvalidasi *request*, data tabungan ada, dan evaluasi jumlah saldo mencukupi (>= nominal). Eksekusi berhasil masuk ke blok *database transaction* untuk memproses pengurangan saldo, mencatat mutasi, membuat log sistem, lalu me-return pesan *success*.

### Tabel Eksekusi Pengujian Whitebox

| Basis Path | Input Pengujian (Skenario) | Jalur yang Dilalui | Hasil yang Diharapkan | Status |
|:---|:---|:---|:---|:---|
| **Path 1** | Mengirimkan `siswa_id` siswa yang tidak punya record tabungan (hasil query `$tabungan` = NULL). Nominal dikirim: Rp 10.000 | 1 -> 2 -> 4 -> 8 | Eksekusi diarahkan ke Node 4, sistem me-return peringatan: "Saldo tabungan tidak mencukupi." | Lulus |
| **Path 2** | Mengirimkan `siswa_id` dengan saldo siswa Rp 15.000, namun menginput nominal penarikan Rp 50.000 | 1 -> 2 -> 3 -> 4 -> 8 | Eksekusi diarahkan ke Node 4 karena evaluasi Node 3 *True*, sistem me-return peringatan: "Saldo tabungan tidak mencukupi." | Lulus |
| **Path 3** | Mengirimkan `siswa_id` dengan saldo siswa Rp 100.000, dan menginput nominal penarikan sebesar Rp 50.000 | 1 -> 2 -> 3 -> 5 -> 6 -> 7 -> 8 | Eksekusi berlanjut ke Node 5 dan 6. Sistem memotong saldo, menambah data mutasi, dan memunculkan *alert*: "Penarikan berhasil dicatat." | Lulus |

---
Tiga jalur independen (*Basis Path*) telah dieksekusi seluruhnya dengan hasil yang sesuai (berhasil diantisipasi oleh *source code*). Karena tidak ada anomali atau celah *logic flow*, modul fungsi Penarikan Tabungan (`tarikStore`) dinyatakan lolos pengujian dan aman digunakan.

# Hasil Wawancara Evaluasi Implementasi Sistem

Untuk mengetahui sejauh mana dampak dari implementasi Sistem Informasi Manajemen Keuangan berbasis digital ini, telah dilakukan pengumpulan tanggapan (wawancara/kuesioner) secara langsung dengan perwakilan pengguna di Yayasan La Tahzan. Mengingat sebelumnya yayasan masih menggunakan pencatatan manual secara penuh, masa transisi ini memberikan kesan tersendiri bagi penggunanya.

Berikut adalah rangkuman hasil wawancara terkait kelebihan dan kekurangan sistem dari kacamata masing-masing responden:

## 1. KH. Asep Saefullah S.pd., M.Pd (Ketua Yayasan)
**Tanya:** "Bagaimana pendapat Bapak setelah yayasan kita mulai beralih menggunakan sistem keuangan digital ini? Apa kelebihan dan kekurangannya menurut Bapak?"

**Jawab:** 
> "Alhamdulillah, perubahannya kerasa banget ya. Kalau dari sisi kelebihannya, sekarang saya sebagai ketua yayasan bisa mantau pergerakan keuangan itu kapan aja. Tinggal buka *dashboard*, saya udah bisa lihat uang masuk berapa, keluarnya buat apa aja. Dulu kan saya harus nunggu laporan fisik dari bendahara numpuk di akhir bulan baru bisa ngecek. Jadi sekarang jauh lebih transparan dan saya rasa lebih aman dari risiko uang bocor atau catatannya hilang."
>
> "Tapi kalau ditanya kekurangannya, ya namanya juga sistem *online*, operasional kita jadi lumayan ketergantungan sama koneksi internet. Terus yayasan juga harus nyiapin dana khusus tiap tahun buat bayar sewa *hosting* sama domainnya. Tapi menurut saya itu sepadan lah sama manfaat yang didapat, itung-itung investasi buat kemajuan sekolah."

## 2. Romanudin S.pd.I (Kepala Sekolah)

**Jawab:**

Sekarang kerjaan mereka jadi lebih cepat selesai, jadi bisa lebih fokus ngurus pelayanan pendidikan yang lain. Terus, buat saya pribadi, jadi gampang banget kalau mau ngecek anak mana saja yang masih nunggak SPP, datanya *real-time*, jadi bisa langsung kita komunikasikan dengan orang tuanya."
>
> "Kekurangannya sih lebih ke masa adaptasinya aja di awal. Staf kita kan udah bertahun-tahun terbiasa pakai kertas, nah pas disuruh pindah ke komputer ini agak kaku awalnya. Jadi kita memang harus luangin waktu ekstra buat ngajarin mereka pelan-pelan biar nggak salah input data pas nerima bayaran."
